**What it is.** The description/docstring is the natural-language contract the model reads to decide *whether* to call a tool and *how* to fill its arguments — purpose, an explicit "use when," and the meaning of each parameter. In MCP it is the `description` field on the tool plus the per-property `description` strings inside `inputSchema` (MCP, 2025). The model never sees your implementation; the description text *is* the tool from its point of view, which makes it the single highest-leverage edit you can make to tool behavior.

**Why / Evidence.** Anthropic (2025) calls prompt-engineering tool descriptions "one of the most effective methods for improving tools," because descriptions are loaded into agent context and directly steer tool-calling; "even small refinements to tool descriptions can yield dramatic improvements." The mental model: describe your tool as you would to a new team member — make implicit context explicit (specialized query formats, niche terminology, resource relationships) rather than assuming the model shares your team's tacit knowledge (Anthropic, 2025). The test is concrete: "Is it obvious how to use this tool, based on the description and parameters, or would you need to think carefully about it?" — if you'd have to think, so will the model (Anthropic, 2024). Give the model room to reason and include example usage, edge cases, input-format requirements, and clear boundaries from other tools; invest in the agent-computer interface (ACI) as much as you would a human-computer interface (Anthropic, 2024). OpenAI (2025) likewise prescribes clear, well-documented tools with descriptive names and parameters so the model selects and invokes them reliably.

**How to apply.** (1) Lead with one sentence of purpose, then an explicit *use when / don't use when* — this is what disambiguates a tool from its near-twins and is the lever on correct *selection*. (2) Write every parameter description as if standalone: what it means, expected format, units, and constraints; prefer semantically meaningful, natural-language values over low-level identifiers (UUIDs, MIME types) the model fumbles (Anthropic, 2025). (3) Put a concrete example call and any usage limits *in the description itself* (rate caps, max page size, "absolute paths only," mutually exclusive args) — the model only reads the contract, not your docs. (4) When two tools overlap, name the boundary in both descriptions ("use X for single lookups, Y for bulk"). (5) Treat it as iterative: write evals, watch where the model picks wrong or malforms args, and refine the wording — the description is the cheapest thing to change and the most impactful.

**Takeaway.** Write the description as a prompt aimed at the model-as-reader: purpose, explicit "use when," self-contained parameter docs, and an in-line example plus limits. It is the cheapest, highest-leverage surface in the whole tool contract — iterate on it against evals ([[tool-evaluation]]).
