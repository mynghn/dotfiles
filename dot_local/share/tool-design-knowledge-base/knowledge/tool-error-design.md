**What it is.** The error a tool returns is part of its contract, not an afterthought. A failed call should hand the agent a next move: name what went wrong *in the call* and how to fix it — the missing parameter, the valid format, the closest legal value, the alternative tool — instead of an opaque code or a raw stack trace. Treat the error string as a micro-prompt the agent reads and acts on, not a signal a human will triage later.

**Why / Evidence.** Anthropic (2025) frames this directly: "if a tool call raises an error (for example, during input validation), you can prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks." A helpful error states the parameter requirement and shows a correctly-formatted example; the agent then retries correctly without burning turns guessing. The MCP spec (2025) makes the plumbing decision that gates all of this: tool *execution* errors (API failures, invalid input data, business-logic errors) must be returned **inside the tool result with `isError: true`** so the model sees them and can self-correct — distinct from protocol errors (unknown tools, invalid arguments, server errors) raised as JSON-RPC errors. An exception that propagates out of the result is invisible to the agent and cannot steer it. (One subtlety: a schema-shape violation is the protocol-level `Invalid arguments` error; it is *semantic* / business validation — like a malformed email — that you return with `isError: true`.) The best error is the one that never fires: Anthropic (2024) calls this poka-yoke — change the arguments so it is harder to make mistakes (e.g., requiring absolute filepaths eliminated a whole class of relative-path errors in their SWE-bench agent) — and recommends finding these failure modes by running many example inputs and watching what the model actually gets wrong.

**How to apply.** Return, don't raise: deliver tool-execution failures in the result where the model reads them, reserving thrown errors for true protocol faults. Make each error answer "what do I do next?" — `email_address must be RFC-5322 format, e.g. user@example.com (got "user at example")` beats `ValidationError: code 422`. Suggest the valid input: echo the allowed enum values, the nearest valid id, or the correct unit. Fail toward the next correct action — on no results, hint a broader query or a sibling tool; on too many, suggest a filter or pagination. Strip stack traces, internal hostnames, and SQL — they spend tokens and tend to send the agent debugging your internals rather than fixing its call. Prevent the error upstream where you can: tighten the schema, constrain enums, make ambiguous arguments unrepresentable. Then iterate empirically: collect the model's real mistakes and rewrite the matching errors until the retry succeeds.

**Takeaway.** An actionable, returned-not-raised error turns a dead end into a guided retry; design errors as guidance toward the next correct call, and design the schema so the most common ones can't happen.

**Boundary.** Generic wording craft for any text belongs to prompt-engineering; managing tool *results* (including errors) already sitting in the window — truncation, compaction — belongs to context-engineering. The error's *content as part of the tool contract* is here. Schema-level prevention (poka-yoke, enums, required fields) is shared with [[input-schema-design]] — here for the error path, there for the input shape itself.
