**What it is.** The discipline of keeping the *active* tool set small and mutually distinct enough that the model reliably selects the correct tool for each step. The failure mode isn't a single bad description — it's the set as a whole: too many choices, or choices that overlap, push the model toward the wrong call or toward inefficient strategies. Levers: prune to high-impact tools, eliminate overlap, group/namespace what remains, and gate tools in and out by context so the model only ever weighs the candidates relevant to its current state.

**Why / Evidence.** Selection accuracy degrades with *confusability*, not raw count. OpenAI (2025) is explicit: "The issue isn't solely the number of tools, but their similarity or overlap. Some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools." So there is no magic number — distinctness is the variable to optimize. Anthropic (2025) warns that "more tools don't always lead to better outcomes" and that too many or overlapping tools "can also distract agents from pursuing efficient strategies," recommending instead a few thoughtful tools targeting specific high-impact workflows rather than wrapping every API endpoint. Anthropic (2024) notes clear inter-tool boundaries matter especially when using many similar tools. When agents consistently select incorrect tools, OpenAI (2025) treats it as a structural signal — first improve clarity, then split the system.

**How to apply.** (1) Curate the set to high-impact, mutually distinct tools rather than broad API-surface coverage. (2) Diagnose wrong-tool selection as an *overlap* problem first: if two tools could plausibly serve the same step, that overlap is the selection bug — sharpen the boundary in their descriptions, or merge them (the merge/split decision itself is [[tool-granularity-and-consolidation]]). (3) Group and prefix related tools (`asana_search`, `asana_projects_search`) so the namespace itself signals which family applies and helps the agent select the right tool at the right time (Anthropic 2025) — see [[tool-naming-and-namespacing]]. (4) Gate by context *for selection*: expose only the candidates valid for the current state so the model weighs fewer confusable options — fewer plausible choices means a more reliable pick. MCP permits a dynamic, changing tool list (`notifications/tools/list_changed`), which is the mechanism that makes context-gating possible (the spec establishes the capability, not a selection benefit per se). Reducing the tool *count* purely to reclaim context-window tokens is a different motive — that budget tradeoff is the `context-engineering-knowledge-base`, not here. (5) When clarity fixes are exhausted and the set is still too large or tangled, split across multiple agents — OpenAI (2025) names tool overload as a split trigger, "if improving tool clarity by providing descriptive names, clear parameters, and detailed descriptions doesn't improve performance." (6) Measure it: an eval that exercises realistic tasks reveals which tools are never correctly chosen or are mutually confused — see [[tool-evaluation]].

**Takeaway.** Optimize the tool set for *distinctness*, not a count. Prune to high-impact tools, kill overlap, namespace the rest, gate by context for selection — and if selection still fails after clarity work, split into multiple agents.

**Boundary.** This entry governs *selectability* — how many tools and how distinct. Merging vs splitting a single capability is [[tool-granularity-and-consolidation]]; prefix conventions are [[tool-naming-and-namespacing]]; wording an individual description well is [[tool-description-writing]]. How many tool *definitions* the context window can afford in tokens (vs. other content competing for the budget) is the `context-engineering-knowledge-base`, not here.
