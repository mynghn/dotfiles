**What it is.** An *enforced* output contract: a JSON Schema attached to a tool call or model response that the runtime constrains the generation to satisfy, so the bytes coming back are guaranteed to parse and match a known shape. Three concrete mechanisms: (1) `strict: true` on function/tool definitions, which forces the model's *argument object* to conform to the function's parameter schema; (2) `response_format` with a `json_schema` and `strict: true`, which constrains the model's *final user-facing answer*; (3) MCP's `outputSchema` on a tool definition, where the server MUST return `structuredContent` conforming to that schema and the client SHOULD validate the returned results against it (MCP, 2025-06-18). This is the machine-checked half of "give me JSON" — distinct from a prose instruction asking for JSON, which nothing enforces.

**Why / Evidence.** Enforcement removes a whole failure class. OpenAI's Structured Outputs guide (2024) frames the payoff as type-safety ("No need to validate or retry incorrectly formatted responses"), programmatically detectable refusals ("Safety-based model refusals are now programmatically detectable"), and simpler prompting ("No need for strongly worded prompts to achieve consistent formatting") — i.e. the schema does the work the prompt otherwise has to beg for, and unreliably. This is strictly stronger than legacy "JSON mode," which guarantees only *syntactically valid* JSON, not adherence to *your* schema. MCP (2025-06-18) makes the same move on the result side: with an `outputSchema`, servers MUST provide structured results conforming to the schema and clients SHOULD validate them, which gives the model reliable type information to parse against. Anthropic's "Writing effective tools for agents — with agents" (2025) is the counterweight: even unenforced, a tool response's structure — XML, JSON, or Markdown — can affect evaluation performance, so the chosen shape is an eval-driven decision, not a default.

**How to apply.** Enforce a schema when a downstream consumer parses the output programmatically — extraction, classification, routing, populating a UI, or chaining the result into the next call — and the cost of a malformed parse is a retry or a crash. Reach for the right mechanism per surface: `strict` for tool *arguments*, `response_format`/`json_schema` for the model's *final answer*, `outputSchema`/`structuredContent` for MCP tool *results*. OpenAI's split: connect the model to tools, functions, and data with function calling, and reserve a structured `response_format` for when it responds to the user. Design the schema for the strict subset that engines actually honor: mark every property `required`, set `additionalProperties: false` to bar invented fields, drop unsupported features (defaults, open-ended types) — model optionality as a nullable union, not an absent field. Keep schemas shallow and flat; deep nesting and sprawling enums degrade adherence and bloat tokens. Handle the refusal branch explicitly — a strict schema is detectable-refusal, not no-refusal. Leave output *free* when the consumer is the model's own reasoning or a human reader, when shape is genuinely open-ended, or when a rigid schema would truncate high-signal prose; per Anthropic, validate the format choice in your tool evals rather than enforcing reflexively. For MCP, still emit the serialized JSON in a text block alongside `structuredContent` for backward compatibility.

**Takeaway.** Enforce the schema exactly where something downstream parses the bytes; pick the mechanism by surface (args vs. final answer vs. MCP result); design to the strict subset (all-required, `additionalProperties:false`, no defaults, shallow); leave it free when the reader is a model or a human.

**Boundary.** The enforced schema lives here. Wording a prose request like "format the answer as JSON" with no machine enforcement is the prompt-engineering sibling's `output-format-instruction` (which cedes the enforced-schema half to this entry).
