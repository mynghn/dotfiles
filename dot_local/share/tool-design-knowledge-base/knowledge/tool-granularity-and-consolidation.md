**What it is.** Granularity is how much work one tool call does: a thin wrapper maps 1:1 onto a single API endpoint; a consolidated tool folds a whole multi-step sequence — or several endpoints — into one call scoped to a task the agent actually performs. The practice is to build tools around the agent's workflow, not mirror the underlying API surface. Consolidate the steps the agent would otherwise have to chain itself, and return only the slice the task needs.

**Why / Evidence.** Anthropic (2025) names the failure mode directly: "A common error we've observed is tools that merely wrap existing software functionality or API endpoints." Endpoints are designed for software with abundant memory; an agent pays attention budget for every intermediate result it must read token-by-token, so chaining `list_users` + `list_events` + `create_event` forces a brute-force search through irrelevant context the agent then has to reason over. Their fixes collapse the chain into one task-shaped tool: `schedule_event` (finds availability and books in one call), `search_logs` instead of `read_logs` (returns only relevant lines plus surrounding context), and `get_customer_context` replacing `get_customer_by_id` + `list_transactions` + `list_notes` (compiles a customer's recent, relevant information at once). The win is twofold — fewer round-trips, and far less intermediate output spent on plumbing — letting the agent "subdivide and solve tasks in much the same way that a human would, given access to the same underlying resources." OpenAI (2025) frames the same target as three tool kinds — data, action, and orchestration (agents-as-tools) — each defined by what it lets the agent *do*, not which endpoint it hits, and cautions that tool trouble is driven more by overlap and similarity than by raw count — an argument against both thin-wrapper sprawl and over-consolidated god-tools that overlap. Anthropic (2024) states the underlying principle: invest in the agent-computer interface (ACI) as much as you would a human-computer one, and design arguments so misuse is hard (poka-yoke).

**How to apply.** Start from the agent's task, not the API catalog: ask "what does the agent need to accomplish in one move?" and make that the tool. Fold deterministic multi-step sequences (lookup → filter → act) into a single workflow tool so the agent never sees the intermediate IDs and lists. Push filtering/search server-side — return relevant rows, not whole tables — so granularity of *output* matches granularity of *intent*. Don't over-consolidate into one god-tool with a dozen mode flags; that just relocates the branching complexity into the schema and creates overlap. Right altitude: one tool ≈ one meaningful unit of agent work. Prune thin wrappers that exist only because an endpoint exists; if no realistic task calls a tool on its own, it shouldn't be a tool.

**Takeaway.** Few high-value, task-shaped tools beat many thin endpoint wrappers: consolidate the chain the agent would otherwise stitch by hand, scope each tool to one unit of work, and return only what that work needs.
