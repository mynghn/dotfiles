# software-digest-ko — 한국어판 실행 계획 (/goal 루프 플레이북)

영어판(`software-digest`, PR #7)과 같은 설계에서 출발하는 **한국어 재구현**이다.
번역이 아니다 — 번역은 영어 관용 위에 얹힌 문장 구조를 그대로 들여와 번역투를
구조적으로 만들기 때문에, [design.md](design.md)의 원칙에서 한국어로 다시
저작한다. 이 문서는 루프가 매 턴 참조하는 실행 정본이다.

## 원천 세 개, 각각의 용법

1. **[design.md](design.md)** — 문제 프레임, 결정 원장, 기각 경로. 사양의 정본.
   원장 #1·#7의 2026-08-05 개정(언어판 쌍, 산출 언어 커밋)까지 반영할 것.
2. **[run-log.md](run-log.md)** — v1 수렴 루프(매트릭스 5회)가 실측으로 얻은
   규칙들. 영어판은 이걸 다섯 번에 나눠 배웠지만 한국어판은 처음부터 내장한다:
   - 부재 주장("여기엔 없다")은 쓰기 전에 문서까지 포함해 검색으로 확정한다.
   - 주장은 그것이 걸친 범위에서 확인한다 — 줄 하나에 대한 주장은 그 줄을
     감싸는 심볼의 경계까지, 소스 전체에 대한 주장은 전수 검색으로.
   - 열거("이 필드를 읽는 세 곳")도 완전성 주장이다. 부정어가 없어도 전수
     검색 대상이다.
   - 압축해서 접어둔 상자는 그 도입 문장에 되비추어 읽는다 — 요약이 자기
     상세와 모순되는 것은 독자가 반드시 발견하는 오류다.
   - 수량(파일 수, 줄 수, 크기)은 쓰는 시점에 소스에서 재계산한다.
   - 검증은 "되읽고 신뢰"가 아니라 "종류별 주장을 전부 나열하고 하나씩
     지우기"로 한다. 살아남는 오류는 의심한 주장이 아니라 목록에 올리지 않은
     주장이다.
3. **`dot_agents/skills/software-digest/`(영어판)** — 번역 소스가 아니라
   **마지막 커버리지 대조표**. 먼저 한국어로 전부 저작한 뒤, 영어판 본문과
   references에 있는 규칙 중 빠뜨린 것이 있는지만 대조한다. 문장 구조를
   가져오지 않는다.

## 저작 규칙

- 시작할 때 로드: skill-design KB에서 description-as-activation-trigger,
  instructions-body-craft, directory-packaging,
  progressive-disclosure-token-economics. 문구를 다듬을 때는 prompt-engineering
  KB INDEX에서 맞는 엔트리만.
- 문체: 컬렉션의 다른 한국어 스킬들(ss-*, ko-quality)과 같은 한다·하라체.
  지시문은 스캔되도록 짧은 명령형으로.
- SKILL.md 본문은 design.md의 원칙에서 재도출한다. **references 4종은 성격이
  다르다** — 거기 담긴 기술적 사실(SVG 프리미티브, 수치, 체크리스트 항목,
  다이어그램 유형표)은 언어 무관 사실이므로 재발견하지 말고 가져와 자연스러운
  한국어로 재서술한다. 가져오지 않는 것은 영어 문장 구조다.

  `../../.agents/skills/software-digest-ko` 한 줄.

**description 초안** (여기서 출발해 다듬는다. YAML 큰따옴표 문자열이므로 내부
인용은 작은따옴표로 — 큰따옴표를 넣으면 파싱이 깨진다):

> 완성된 개발 작업물을 처음 받아든 사람이 빠르고 정확하게 이해하도록, 자기완결
> HTML 다이제스트 한 장을 한국어로 만들고 그 앞뒤의 이해 세션을 함께 진행한다 —
> 쓰기 전에 독자의 목적·사전 지식·읽기 예산을 짧게 확인하고, 전달 후에는 자기
> 점검을 제안한다. 입력은 전달된 작업물이면 무엇이든 된다: PR 하나 또는 여러 개,
> 레포지토리 하나 또는 여러 개, diff나 커밋 범위, 맥락이 담긴 이슈·티켓, 혹은
> 이들의 혼합 — 여러 레포에 걸친 작업도 하나의 대상이다. 동료가 끝낸 변경을
> 리뷰 전에 파악해야 할 때, 낯선 서비스에 온보딩할 때, 인수인계를 받을 때,
> 도입을 검토하는 오픈소스를 가늠할 때 사용한다. '이 PR 파악해줘', '이 레포
> 이해하게 해줘', '인수인계 받았어', '이 변경이 실제로 뭘 하는 거야' 같은 요청이
> 신호다. 이미 특정된 개념 하나를 설명하거나 아는 함수 하나에 답할 때는 스킬
> 없이 바로 답한다.

트리거 문구는 지어낸 것이 아니라 사용자가 실제로 쓴 말에서 왔다(시나리오
호출문과 실사례 요청). 영어판과의 라우팅은 description 언어 + "한국어로" 구절
두 신호로 성립하므로 영어판을 언급하지 않는다.

## 불변 계약 — 기계 훅은 언어와 무관하게 동일

`check.py`가 아래 마크업을 그대로 검사한다. 산문은 한국어라도 클래스·속성
이름은 바꾸지 마라:

- `<section class="reader-contract">` (독자·전제·분량·다루는 것·빼는 것·읽은
  상태의 핀: 레포별 브랜치·커밋)
- `<section class="self-check">` (예측·설명·위치파악을 아우르는 3문항 이상)
- `<code class="anchor" data-path="…" data-line="…">` — 대상이 레포 여럿이면
  `data-repo` 필수
- `data-basis="verified|stated|inferred"`, `stated`에는 `data-source`
- 러너의 `session-log.md`: `## GATE` → `## CONTRACT` → `## DIGEST WRITTEN` 순서

## 한국어 품질

저작 시점부터 ko-quality의 정본 원칙(번역투·AI 상투어 회피, 문장 리듬)을
적용하고, SKILL.md + references 4종이 완성되면 **첫 매트릭스 전에 ko-quality
중량 검수 파이프라인을 1회** 돌려 교정한다. 스킬 자체는 ko-quality에 의존하지
않는다 — 이것은 저작 세션의 품질 관리일 뿐이다.

## 검증 — 하네스는 그대로 재사용

- 실행: `SD_SKILL=software-digest-ko ./evals/run.sh` (전 시나리오),
  `… ./evals/run.sh s1-bubbletea-pr` (부분). `check.py`는 `SD_SKILL`로 검사
  대상 스킬을 고른다 — 동결 커밋 `e996b3a`에서 파라미터화됨.
- 시나리오·픽스처·`rubric.md`는 v1 것을 그대로 쓴다. 호출문·페르소나가 이미
  한국어라 재작성이 없다. red 상태는 준비 시점에 확인됨(스킬 부재로 skill 섹션
  FAIL); rubric과 체커는 v1 레드 테스트로 이미 증명됐다.
- 시나리오 러너와 L4 저지는 항상 프레시 서브에이전트, 메이커와 분리.
- **매트릭스** = run.sh 전 체크 + 시나리오별 L4 저지(9항목 × 3). 진행 기록은
  `run-log-ko.md`에 남긴다(매트릭스마다 결과 표와 실패 원인).
- `evals/`는 `e996b3a` 이후 수정 금지. 매 턴 최소 1회 커밋.

### 러너·저지 디스패치에 반드시 넣을 것

v1의 다섯 매트릭스를 거치며 디스패치 프롬프트에 누적된 지침이다. rubric.md는
그 이전에 동결되어 이것들을 담지 못했으므로, 서브에이전트를 띄울 때 프롬프트에
직접 포함하라. (v1에서 이 강조들이 빠진 저지는 해당 결함을 통과시켰다.)

**러너에게:**
- 픽스처는 수정 금지. 실험(테스트 실행, 훅 되돌리기)은 스크래치패드 사본에서
  하고, 끝나면 픽스처의 `git status`가 깨끗함을 확인해 보고하라.
- 다이제스트는 한 번의 거대한 쓰기가 아니라 적당한 크기로 나눠 이어 써라
  (v1에서 과대 단일 쓰기가 연결 오류로 유실된 전례가 있다).

**저지에게 (rubric 항목 3·4·6에 겹쳐서):**
- 다이제스트가 말하는 모든 수량(파일 수·줄 수·크기·범위)이 소스와 일치하는지
  재계산으로 확인하라.
- 소스 전체를 한정하는 주장은 실제 전수 검색으로 확인하라 — 부정형("~뿐",
  "없다")과 열거형("~하는 세 곳") 모두. 열거는 부정어 없이도 완전성 주장이다.
- 앵커가 심볼(함수·클래스)을 명명하면, 그 심볼의 경계가 인용된 줄을 실제로
  감싸는지 확인하라. 옆 헬퍼에 있는 줄은 항목 4의 FAIL이다.
- 접힌 상자마다 그 도입 문장에 되비추어 읽어라 — 요약이 자기 상세와 모순되면
  fidelity FAIL이다.
- 엄격하게 판정하라: 잘 읽히더라도 항목에 어긋나면 그 항목은 FAIL이다.
  픽스처를 직접 열어 검증하고, 산출물을 수리하지 말고, 지정된 출력 형식만
  반환하라.

## 종말 상태

성공(연속 2턴 풀 매트릭스 전항목) / 정체(같은 체크 3턴 연속 실패 → 원인 보고) /
소진(25턴). v1의 교훈: 종료 조건의 탈출구는 별도 문단이 아니라 **완료 조건의
선언지**로 넣는다 — /goal 평가기는 완료 조건만 판정하므로, 바깥에 적힌 중단
조건은 평가기가 인지해도 훅을 풀지 못한다. 아래 프롬프트가 그 형태다. /goal의
성공은 "사람 검토 준비 완료"이지 품질 확정이 아니다 — 최종 수용(L5)과 영어판
대비 비교는 사용자의 몫으로 남는다.
